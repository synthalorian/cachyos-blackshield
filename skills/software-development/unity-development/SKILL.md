# Unity Development Workflow

## 1. Project Audit (AI-Generated Code)

When inspecting a Unity project that was generated by another model, follow this order:

### Phase A — Map the Territory
1. `search_files(target='files')` for `*.cs`, `*.unity`, `*.prefab`, `*.asset` — understand what exists
2. **Count code files vs data files** — compute the ratio:
   - `find Assets -name '*.cs' | wc -l` = C# scripts
   - `find Assets -name '*.unity' | wc -l` = scenes
   - `find Assets -name '*.prefab' | wc -l` = prefabs
   - `find Assets -name '*.asset' | wc -l` = ScriptableObject assets
   - If scripts >> everything else combined (e.g. 120+ .cs with zero .unity/.prefab/.asset), this is a **code-only project** — see Phase A.3
3. Read ALL `.cs` files to understand:
   - Namespace structure (should be consistent, e.g. `Holylands.X`)
   - Singleton patterns (typically `MonoBehaviour` + static `Instance`)
   - Event bus pattern (if present, note event IDs)
4. Identify duplicates (same class in two files, same file in two locations)

### Phase A.3 — Code-Only Project Assessment

When a Unity project has all scripts but **zero scenes, prefabs, or ScriptableObject assets**:

1. **Read `Assets/Scripts/Data/` or equivalent data-type files** — understand what SO types exist (CharacterDataSO, SkillDataSO, ItemDataSO, EnemyDataSO, etc.)
2. **Check `[CreateAssetMenu]` attributes** on every data class — if they all have proper menu paths, the data layer is ready but unpopulated
3. **Check `Packages/manifest.json`** — identify required packages (input system, TMP, sprite/tilemap, timeline, etc.)
4. **Read `ProjectSettings/ProjectVersion.txt`** — note the Unity version
5. **Cross-reference README roadmap vs actual code** — list which systems are fully coded, which are stubs, which are referenced in the README but don't exist
6. **Determine if the project was migrated** — check `.gitignore` for non-Unity artifacts, scan git history for telltale commit messages ("Initial Grid Snapshot", "migrated from UE5", etc.). Migrated projects often lose their binary assets (scenes, SO files, sprites)

**Output**: A clear two-category report:
- **Code complete**: Systems that have full C# implementations (ready to wire up with data)
- **Missing data layer**: ScriptableObject types that exist as C# classes but have zero `.asset` files in the project
- **Missing scene infrastructure**: Number of scenes that need to be created (bootstrap, main menu, overworld, battle, etc.)

### Phase B — Find Compile-Killing Bugs (fix priority order)

When the project has a `docs/MASTER_PLAN.md`, `ROADMAP.md`, or embedded bug list:

1. **Identify claimed issues**: Scan for sections like "Files That Need Fixing Immediately" or "Known Bugs"
2. **For each claimed issue, read the actual code** — never take the plan at face value. Bugs claimed as "broken" may already be fixed, and the plan may describe a different bug than what's actually in the code
3. **Categorize each claim**:
   - ✅ **Fixed** — code has the fix, plan is stale
   - ✗ **Still broken** — code matches the claimed bug
   - 🔍 **Different than claimed** — the bug exists but manifests differently (e.g. "E button collision" is actually West, not East)
   - ❓ **Already correct** — code is fine, plan was wrong about the issue
4. **Log the delta** — the output should be a clear list: what the plan says vs what the code does, grouped by "needs fixing" vs "already handled"

### Phase B — Find Compile-Killing Bugs (fix priority order)
1. **Duplicate files** — delete the wrong one first
2. **Missing types** — classes referenced but never defined (NPCData, GOAPBehavior, etc.)
3. **Wrong API calls** — these are the most common Unity pitfalls (see below)
4. **Namespace mismatches** — `using` statements point to wrong namespace
5. **Syntax errors** — missing dots, wrong operators, wrong method signatures

### Phase C — Fix Missing Logic
1. Commented-out code that should be wired up (quest rewards, save calls)
2. Event handlers that subscribe to events but never do anything
3. Runtime-generated UI/TEMP objects with no cleanup

### Phase D — Create Setup Documentation
1. Step-by-step guide from project open → first play
2. Package requirements (Input System, TMP, etc.)
3. Scene creation order (bootstrap → main menu → game world)
4. ScriptableObject creation per data type

## 2. Common Unity C# Pitfalls

### Pitfall: Duplicate files
Two files with the same class, or a file in the wrong location with the wrong name.
**Fix**: Delete the duplicate, merge improvements into the canonical file.

### Pitfall: `Mathf.Clamp01` vs `Mathf.Clamp`
`Mathf.Clamp01(x)` clamps to 0.0–1.0. If your variable is 0–100 scale, use `Mathf.Clamp(x, 0f, maxValue)`.
**Pattern**: Always check what scale the variable uses before picking clamp.

### Pitfall: `AudioSource` doesn't have `.lowPassFilter`
`AudioLowPassFilter` is a **separate component**, not a property on AudioSource.
**Fix**: `var filter = sourceObj.AddComponent<AudioLowPassFilter>(); filter.cutoffFrequency = value;`
**Pattern**: When a property doesn't exist on a Unity component, it's probably a separate component.

### Pitfall: UIManager infinite toggle loop
Calling `ToggleInventory()` inside `Update()` when `_isInventoryOpen == true` creates an infinite loop — toggles open, toggles closed, next frame toggles open again.
**Fix**: Only toggle on input events (button press), never poll state in Update.

### Pitfall: Missing `using System;`
`Guid`, `DateTime`, and other System types need `using System;` at the top. Unity projects don't always have it.
**Fix**: Add the using directive.

### Pitfall: Event data type mismatches
System A publishes `WeatherType` enum, System B subscribes expecting `string`.
**Fix**: On the receiving end, call `.ToString()` on the data object, or handle multiple types.

### Pitfall: Anonymous type in event bus
Publishing `new { Faction = x, Amount = y }` — the receiver can't cast it to a known type.
**Fix**: Use reflection to read properties, or define a proper class/struct for the event data.

### Pitfall: Dual stamina/health management across systems

Two different systems (e.g. `PlayerController` and `MovementController`) both track their own `_stamina`/`_faith`/`_health` values independently. They fire events but never actually sync — PlayerController.Stamina changes don't propagate to MovementController._stamina and vice versa. The values drift apart immediately.

**Detection**: Scan for `private float _stamina`, `public float stamina`, or `float health` in multiple classes. If more than one MonoBehavior owns the raw value, they'll fight.

**Fix**: Pick ONE authoritative owner (typically CombatController or PlayerController). All other systems read from it via public properties or events. The owner should NOT set values in Update() — only respond to events from the authoritative system.

### Pitfall: Gamepad input binding collisions

Multiple actions bound to the same `<Gamepad>/West`, `<Gamepad>/East`, or `<Gamepad>/South` button. Works fine on keyboard (where each action has a unique key) but on gamepad one button triggers two or three different actions simultaneously.

**Detection**: In `InputManager.cs`, list every `AddBinding("<Gamepad>/...")` call. Group by button name — any button used more than once is a collision.

**Fix**: Either (a) remove duplicate gamepad bindings so each button maps to exactly one action, or (b) use composite bindings with modifiers (hold vs tap) to differentiate.

### Pitfall: Dead skeleton directories

Accidental directories with special characters in the name — e.g. `{Assets/` instead of `Assets/` (braces in folder names cause import issues). These are typically empty or contain only empty subfolder stubs.

**Detection**: `ls` the project root and look for unexpected directory names with braces, brackets, or misspellings.

**Fix**: `rm -rf` the dead directory. If it contains anything non-empty, merge contents into the correct location first.

### Pitfall: EnemyController NRE on target subscription

EnemyController subscribes to `EventSystemManager` in `Start()`, and the event handler accesses `target.position` — but `target` may not be set yet (it's set later via `SetTarget()` by the spawner). If the player passes by before the enemy's target is assigned: NRE.

**Detection**: Look for `target.position`, `target.transform`, or any `target.` access inside event handlers (`OnPlayerMoved`, etc.) without a null guard on `target`.

**Fix**: Guard every event handler with `if (target == null) return;` before accessing target members.

### Pitfall: Function that computes but never applies

A combat or action method computes all the damage values, applies stance modifiers, weapon multipliers, armor penetration — then logs the result and returns. It never calls `TakeDamage()` on the target. The numbers look right in the console, but nothing actually happens to the enemy's health.

**Detection**: Follow the call chain from every `Attack()` / `DealDamage()` function. Does it ever invoke `TakeDamage()` on an enemy or player target? If the last thing is `Debug.Log()` and an event publish, the actual HP mutation is missing.

**Fix**: Add the actual HP mutation call (typically `target.TakeDamage(finalDamage, damageType)`) at the end of the computation chain.

### Pitfall: File named wrong containing a different class

A file named `GameEvent.cs` might contain `GameBootstrapper` instead of `GameEvent`. This is common in AI-generated code where the model regurgitates the wrong class into a file with a plausible name. The file name should match the class name.

**Detection**: Read the file and look at its namespace + class declaration.

**Fix**: Delete the wrong file. If its content has unique code (improvements over the canonical file), merge those improvements into the correct file first, then delete.

### Pitfall: Singleton syntax bugs

Missing dots (`singletonObj DontDestroyOnLoad` instead of `DontDestroyOnLoad(singletonObj.gameObject)`), wrong method signatures.
**Fix**: Always double-check the static call syntax — Unity APIs are static methods.

## 3. Unity vs Unreal Decision

For a solo dev with an existing codebase, Unity is the pragmatic choice when:
- Code already exists in C# with MonoBehaviour patterns
- Game is mid-scale (not AAA photorealistic open world)
- Project uses region-based zones, not seamless streaming
- Developer has C#/.NET experience
- Faster iteration cycles matter more than absolute graphical fidelity

Unreal only wins for:
- AAA photorealistic visuals with Nanite/Lumen
- Large dedicated team with C++ expertise
- Seamless open world streaming requirement

1. **Install csharp-ls** via dotnet tools:
   ```bash
   dotnet tool install --global csharp-ls
   ```
2. **Add dotnet tools to PATH** in shell config:
   ```bash
   echo 'export PATH="$PATH:$HOME/.dotnet/tools"' >> ~/.bashrc
   ```
3. **Create LazyVim plugin file** at `~/.config/nvim/lua/plugins/csharp-unity.lua`:
   - Register `csharp_ls` in lspconfig opts

## 7. Unity-MCP Integration

Unity-MCP ([github.com/CoplayDev/unity-mcp](https://github.com/CoplayDev/unity-mcp)) bridges Unity Editor and AI agents via MCP. It gives the agent direct access to scenes, prefabs, components, and assets.

### Architecture

```
AI Agent (Hermes)  ←→  Python MCP Server (uvx)  ←→  Unity Plugin (MCPForUnity)
    stdio transport        localhost bridge           Unity Editor process
```

### Hermes-Side Setup

Add this entry to `~/.hermes/config.yaml` under `mcp_servers`:

```yaml
mcp_servers:
  unity:
    command: uvx
    args:
    - --from
    - mcpforunityserver
    - mcp-for-unity
    - --transport
    - stdio
```

### Unity-Side Setup

1. Open Unity project
2. **Window → Package Manager → + → Add package from git URL...**
3. Enter: `https://github.com/CoplayDev/unity-mcp.git?path=/MCPForUnity#main`
4. **Window → MCP for Unity → Start Server**
5. Confirm green status: 🟢 Connected ✓

### Connection Lifecycle

- The Python server only starts successfully when Unity is running with the plugin active
- If Unity isn't running when Hermes starts, the `uvx` command will fail and log an error
- Connection is persistent once established — tools auto-register with `mcp_unity_` prefix
- To reconnect after Unity restarts: restart Hermes or trigger MCP rediscovery

### Agent Capabilities (once connected)

The agent can call tools to:
- Create/modify scenes, spawn prefabs, edit component values
- Run play-mode tests and inspect results
- Manage project assets (rename, move, organize)
- Query scene state (list objects, read component properties)

### Known Limitation

The agent cannot connect to Unity-MCP from `delegate_task` subagents — child sessions lack the MCP toolset by default. Set `toolsets: [terminal, file]` or add `mcp` to enabled toolsets if needed; the subagent won't see `mcp_unity_*` tools unless the parent connection was established at startup.

## 8. Code-First Data Registry (No-Editor Bootstrap)

When a Unity project has 100+ C# scripts but **zero ScriptableObject .asset files** (common after engine migration or code-generation bursts), create an in-memory data registry. This lets the project boot and test without opening Unity.

### When to Use

- Project has all SO class definitions (`[CreateAssetMenu]` attributes) but zero `.asset` files
- `Resources.Load<X>()` calls will all return null at runtime
- You cannot (or choose not to) open Unity Editor to create assets
- Game data is defined entirely in C# and can be hardcoded

### Architecture

```
DefaultGameData (static class)
  ├── Initialize() — idempotent, called once
  ├── Generates ALL data via ScriptableObject.CreateInstance<T>()
  ├── Stores in Dictionary<string, ScriptableObject> cache
  └── Exposes FindSkill(), FindItem<T>(), FindCharacter(), FindEnemy(), Get<T>()

GameInitializer (MonoBehaviour)
  ├── Bootstrap() — calls DefaultGameData.Initialize()
  ├── Populates manager arrays (ChapterManager.chapters, etc.)
  └── StartNewGame() — creates starting party + chapter 1

Patched systems
  └── Resources.Load<T>() → fallback → DefaultGameData.FindX()
```

### Implementation Pattern

```csharp
// In DefaultGameData.cs
public static class DefaultGameData
{
    private static Dictionary<string, ScriptableObject> _cache = new();
    private static bool _initialized;

    public static void Initialize()
    {
        if (_initialized) return;
        _initialized = true;
        GenerateItems();
        GenerateSkills();
        // ... per-category generators
    }

    private static T Create<T>(string key) where T : ScriptableObject
    {
        var obj = ScriptableObject.CreateInstance<T>();
        obj.name = key;
        _cache[key] = obj;
        return obj;
    }

    private static SkillDataSO NewSkill(string key, System.Action<SkillDataSO> setup)
    {
        var s = Create<SkillDataSO>(key);
        setup(s);
        return s;
    }
}
```

### Resources.Load Fallback Pattern

Find every `Resources.Load<T>()` call in the codebase. For each one that loads game data (skills, items, characters, enemies), add a fallback to the registry:

```csharp
// Before
var skill = Resources.Load<SkillDataSO>($"Skills/{name}");

// After
var skill = Resources.Load<SkillDataSO>($"Skills/{name}");
if (skill == null)
    skill = DefaultGameData.FindSkill(name);
```

Key `Resources.Load` paths to patch:
- `Resources.Load<SkillDataSO>($"Skills/{name}")` → `FindSkill()`
- `Resources.Load<ItemDataSO>($"Items/{name}")` → `FindItem<ItemDataSO>()`
- `Resources.Load<CharacterDataSO>($"Characters/{name}")` → `FindCharacter()`
- `Resources.Load<EnemyDataSO>($"Enemies/{name}")` → `FindEnemy()`
- Any `Resources.Load<GameObject>` for VFX/prefabs — these must exist as actual prefabs (cannot be code-created easily)

### Pitfalls

- **ScriptableObject.CreateInstance<T>()** must be called, not `new T()`. SOs are special Unity objects that require `CreateInstance`.
- **Don't store in Resources/** — the whole point is avoiding needing assets on disk. Store the instances in a static dictionary instead.
- **GameInitializer must exist in the scene** — it's a MonoBehaviour that runs on Start/Awake. Without it in the bootstrap scene, the registry won't populate.
- **Static data is read-only at edit time** — values set in code can't be tweaked in the inspector. This is a bridge, not a replacement for proper SO assets later.
- **Encounter tables and random events often need manual population** — check if the system has a `GenerateDefault()` method or relies on inspector assignment.
- **The `name` field on ScriptableObject instances** matters if any code compares `obj.name` — set it explicitly via `obj.name = key`.

## 9. ScriptableObject-First Architecture

A clean architectural pattern where ALL game data is defined as `ScriptableObject` assets rather than hardcoded in MonoBehaviours.

### Why It Matters

- **Decouples data from logic** — designers (or other AI agents) can create/modify game data without touching code
- **Runtime hot-reload** — SO values change in-editor without recompiling
- **Modular** — each weapon, enemy, quest, item is its own `.asset` file that can be individually version-controlled

### Implementation Pattern

```csharp
// CreateAssetMenu attribute at the bottom of the class
[CreateAssetMenu(fileName = "NewWeapon", menuName = "Game/Data/Weapon")]
public class WeaponData : ScriptableObject
{
    public string weaponId;
    public string displayName;
    public WeaponTier tier;
    public float baseDamage;
    public float armorPenetration;
    public float attackSpeed;
    // ... stats
}
```

### Folder Layout

```
Assets/ScriptableObjects/
├── Weapons/     (WP_Longsword.asset, WP_Mace.asset, etc.)
├── Armor/       (AR_Chainmail.asset, etc.)
├── Items/       (IT_Bandage.asset, IT_HolyWater.asset, etc.)
├── Enemies/     (EN_SaracenFootman.asset, etc.)
├── Skills/      (SK_HeavyStrike.asset, etc.)
├── Factions/    (FC_Templars.asset, etc.)
└── Quests/      (QS_PilgrimsFirstStep.asset, etc.)
```

### Convention

- SO files prefixed by type: `WP_` for weapons, `AR_` for armor, `IT_` for items, `EN_` for enemies, `SK_` for skills, `FC_` for factions, `QS_` for quests
- Menu paths nested under a game-specific root: `Create → The Holy Lands → Data → Weapon Data`

## 10. Singleton → VContainer DI Migration

When a Unity C# codebase has pervasive `public static Xxx.Instance` singleton patterns, no DI framework, and hardcoded data in C# classes, migrate it to VContainer Dependency Injection. This is the same pattern used for Blood Legacy (Godot→Unity rewrite) and Holy Lands (62-file singleton cleanup).

### When to Migrate

Signals that a project needs this treatment:
- `grep -rn "public static.*Instance" Assets/Scripts/ | wc -l` returns 10+
- `grep -rn "EventSystemManager.Instance.Publish" Assets/Scripts/ | wc -l` returns 20+
- Systems reference each other via `Xxx.Instance.Method()` instead of injected references
- Hardcoded data in C# classes (`ItemDatabase.cs`, `QuestContent.cs`, etc.) instead of ScriptableObject `.asset` files
- No DI framework (no VContainer, Zenject, or Extenject in `Packages/manifest.json`)
- Project has zero `.unity` scenes, zero `.prefab` files, zero `.asset` files — code-only

### Migration Sequence

#### Phase 1 — Foundation (create these files first)

Create the DI infrastructure before touching any system:

```
Assets/Scripts/Core/DI/GameLifetimeScope.cs   — Root VContainer scope
Assets/Scripts/Core/DI/GameplayScope.cs        — Per-scene scope
Assets/Scripts/Core/Events/IEventBus.cs        — Event bus interface
Assets/Scripts/Core/Events/EventBus.cs         — Event bus implementation
Assets/Scripts/Core/Interfaces/IGameServices.cs — ALL service interfaces
```

**GameLifetimeScope.cs pattern:**
```csharp
public class GameLifetimeScope : LifetimeScope
{
    protected override void Configure(IContainerBuilder builder)
    {
        builder.Register<IEventBus, EventBus>(Lifetime.Singleton);
        builder.Register<IFaithService, FaithSystem>(Lifetime.Singleton);
        builder.Register<IWorldService, WorldSystem>(Lifetime.Singleton);
        // ... all services
        builder.RegisterEntryPoint<GameEntryPoint>();
    }
}
```

**EventBus.cs** — replaces the old `EventSystemManager.Instance.Publish()` pattern:
```csharp
public class EventBus : IEventBus
{
    private readonly Dictionary<GameEvent, List<Action<object>>> _listeners = new();

    public void Publish(GameEvent evt, object data = null)
    {
        List<Action<object>> safeCopy;
        lock (_listeners) { /* copy and iterate */ }
    }
    // Subscribe(), Unsubscribe(), Clear()
}
```

**IGameServices.cs** — ONE file with ALL interfaces:
```csharp
public interface IFaithService : IGameService { /* ... */ }
public interface IMiracleService : IGameService { /* ... */ }
public interface IPlayerService { /* ... */ }
// 20+ interfaces in one file
```

#### Phase 2 — Convert Each System (file-by-file or batch)

For each system file, apply these transforms:

**Step 1:** Add VContainer using:
```csharp
    using Holylands.Core.Interfaces;
    using Holylands.Events;
    using VContainer;
```

**Step 2:** Replace static Instance with IEventBus field + Inject:
```csharp
// BEFORE:
public class FaithSystem : MonoBehaviour, IBootstrappable
{
    public static FaithSystem Instance { get; private set; }
    
    public void Initialize()
    {
        Instance = this;
        // ...
    }
    
    private void Update()
    {
        EventSystemManager.Instance.Publish(GameEvent.PlayerFaithChanged, amount);
    }
}

// AFTER:
public class FaithSystem : MonoBehaviour, IFaithService
{
    private IEventBus _eventBus;
    
    [Inject]
    public void Construct(IEventBus eventBus)
    {
        _eventBus = eventBus;
    }
    
    public void Initialize()
    {
        // No Instance assignment
    }
    
    private void Update()
    {
        _eventBus?.Publish(GameEvent.PlayerFaithChanged, amount);
    }
}
```

**Step 3:** Replace all singleton cross-references with FindObjectOfType (temporary bridge):
```csharp
// BEFORE:
WorldSystem.Instance.currentRegionId

// AFTER:
FindObjectOfType<WorldSystem>()?.currentRegionId
```

**Step 4:** For the SaveSystem (serialization hub that touches every system), inject dependencies directly or use FindObjectOfType for all cross-references.

#### Phase 3 — Batch Convert with Python Scripts

For large codebases (30+ files), write a Python script to batch-apply the mechanical transformations:

```python
# Batch conversion patterns:
REPLACEMENTS = {
    "FaithSystem.Instance": "FindObjectOfType<FaithSystem>()",
    "WorldSystem.Instance": "FindObjectOfType<WorldSystem>()",
    "EventSystemManager.Instance.Publish(": "_eventBus?.Publish(",
    "EventSystemManager.Instance.Subscribe(": "_eventBus?.Subscribe(",
}
```

The script reads each file, applies all replacements, adds `using VContainer;` if missing, removes static Instance declarations via regex, and adds the Inject method before Awake(). See `references/unity-di-migration-batch-script.md` for the complete script template.

### Per-System Conversion Patterns

| System Type | Changes |
|-------------|---------|
| **Core services** (Faith, Economy, Quests) | Remove Singleton<T>, add `[Inject] IEventBus`, implement interface, register in GameLifetimeScope |
| **Player systems** (Controller, Combat, Movement) | Remove static Instance, add `[Inject] IEventBus`, keep scene-MonoBehaviour registration via `RegisterComponentInHierarchy<T>()` in GameplayScope |
| **World systems** (Weather, FastTravel, Encounters) | Same as core services |
| **SaveSystem** | Remove Singleton<T>, inject ALL services it serializes via constructor OR use FindObjectOfType fallbacks |
| **Data databases** (ItemDatabase, QuestContent, EnemyDatabase) | Keep as-is during migration, will convert to ScriptableObjects in next phase |

### Pitfalls

- **`using VContainer;` must be in every file that uses `[Inject]`** — the batch script should add this
- **Remove `Instance = this;` from Awake/Initialize** — the batch script's regex catches most but double-check files that set Instance at a different lifecycle point
- **Cross-file `.Instance` references** — after removing static Instance from A, every file that referenced `A.Instance` breaks. The batch script must replace ALL occurrences, not just the declaration
- **SaveSystem is the hardest** — it serializes data from every system. Either inject all services (constructor gets 8+ params) or use FindObjectOfType helpers for everything
- **Test files** — 58+ unit tests that call `Xxx.Instance.Method()` will all break. Update them last, using FindObjectOfType or inject a test-specific service locator
- **Events with `?.` operator** — `WorldSystem.Instance?.currentRegionId` (null-conditional) has a different pattern than `WorldSystem.Instance.currentRegionId`. Ensure the batch script handles both
- **Don't forget scene-specific systems** — PlayerController, CombatController, MovementController, InputManager, UIManager exist in the scene hierarchy. Register via `RegisterComponentInHierarchy<T>()` in GameplayScope, not in the root scope

### With Unity-MCP

When Unity-MCP is connected, the migration can be verified by:
1. Opening the project in Unity (which triggers C# compilation)
2. Checking the Unity Console for compile errors
3. Inspecting the VContainer diagnostics (Window → VContainer → Diagnostics)
4. Pressing Play and monitoring for null reference exceptions on injected services

Without Unity-MCP, the migration is code-only — compile errors will only show when Unity opens the project.

- `references/unity-di-migration-batch-script.md` — Complete Python batch conversion script template for mass file transformation

### Pattern

```
project-root/
├── Assets/                  # Unity scripts (C#)
│   └── Scripts/
├── Source/                  # UE5 source (C++)
│   └── Holylands/
│       ├── Public/          # .h header files
│       └── Private/         # .cpp implementation files
└── docs/                    # Shared design docs
```

### Keeping Both in Sync

- **Architecture is shared** — the event bus, singleton patterns, and state machines are the same in both codebases
- **Data structures are mirrored** — WeaponData, ArmorData, AttackData exist in both Unity `[System.Serializable]` form and UE5 `USTRUCT(BlueprintType)` form
- **Combat logic is the first port** — it's the most performance-critical system and benefits most from UE5's Chaos physics
- **Hit detection** — Unity uses raycast/spherecast, UE5 uses `LineTraceByChannel` — same logic, different API
- **Event bus** — Unity: custom `EventSystemManager` with `Publish/Subscribe`. UE5: `UHolylandsEventSystem` with `Publish/PublishFloat` using UE5's native delegates

### When to Update Which

- **Unity first** for gameplay logic iteration (faster compile, easier scripting)
- **Port to UE5** when: physics fidelity matters (parry windows, hitboxes), visuals need Nanite/Lumen, or the prototype is validated and you need AAA polish
- **Keep UE5 stubs** — even placeholder implementations let you catch API/architecture mismatches early

## 7. Pitfall: File Named Wrong Containing Duplicate Class

A file named `GameEvent.cs` might contain `GameBootstrapper` instead of `GameEvent`. This is a common artifact of AI-generated code where the model regurgitates the wrong class into a file with a plausible name.

**Detection**: read the file and look at its namespace + class declaration. The file name should match the class name.

**Fix**: Delete the wrong file. If its content has unique code (improvements over the canonical file), merge those improvements into the correct file first, then delete.
