# Full-Stack Web Features (Node + Express + React + Drizzle)

## Overview
Pattern for adding end-to-end features to a TypeScript full-stack web app:
Express 5 backend → React/Vite frontend → Drizzle ORM → PostgreSQL.

## Architecture Layer Order (always build this way)

```
1. Database schema (drizzle pgTable)      ← the data contract
2. SQL migration (manual or drizzle generate) ← commit the schema
3. Service layer (business logic)          ← CRUD + queries
4. Express routes (HTTP handlers)          ← wire the service
5. Register route in index.ts              ← app.use()
6. Frontend types (types.ts)               ← mirror backend types
7. Frontend API client (client.ts)         ← fetch wrappers
8. Frontend React component                ← views + state
9. Wire component into App.tsx + Sidebar   ← navigation
10. CSS styles for the component           ← theme-var driven
```

## Express 5 Pitfall: `req.params` is `string | string[]`
Express 5 types changed. `req.params.id` is no longer `string` — it's `string | string[]`.

**Fix**: Define a helper at the top of every route file:
```typescript
function paramStr(p: unknown): string {
  return Array.isArray(p) ? p[0] : String(p || '');
}
```
Then use `paramStr(req.params.id)` everywhere. Same pattern for query strings.

## Drizzle ORM: Multi-Schema Config
If your project has multiple schema files (e.g. `schema.ts`, `schema.auth.ts`, `schema.bots.ts`, `schema.souls.ts`), drizzle-kit will **only** track the files listed in `drizzle.config.ts`.

**Fix**: Pass an array to the `schema` field:
```typescript
schema: ['./src/db/schema.ts', './src/db/schema.auth.ts', './src/db/schema.bots.ts', './src/db/schema.souls.ts'],
```

**Migration workflow**:
- `npx drizzle-kit generate` — produces numbered SQL files from schema
- `npx drizzle-kit push` — direct schema push (interactive; use `--force` to auto-confirm)
- `npx drizzle-kit push --force` — non-interactive apply (use when push asks about renames)
- **Or** apply generated SQL directly: `psql -d janus -f drizzle/000N_name.sql`
- **For manual SQL migrations** (not generated by drizzle): create numbered files like `drizzle/0002_soul_tables.sql` and apply with `psql -d janus -f drizzle/0002_soul_tables.sql`
- **Wrap manual migrations in a transaction** (`BEGIN; ... COMMIT;`) so partial failures roll back cleanly
- **For standalone raw SQL** (tables not in drizzle schema), use `CREATE TABLE IF NOT EXISTS` to make migrations idempotent

**PITFALL: Drizzle push gets confused by existing tables** — If you have manually-created tables that match drizzle's schema, `drizzle-kit push` may prompt "Is this table created or renamed from another table?" Use `--force` to skip the prompt. If that still fails, apply the generated SQL directly with `psql` instead.

**PITFALL: FK references in SQL migrations** — Drizzle creates tables in schema.ts (e.g. `users`, `channels`). If your SQL migration references these tables (e.g. `REFERENCES users(id)`), the SQL file must be applied AFTER the Drizzle-generated migration that creates those tables. Apply them in order: `0000_core.sql → 0001_auth.sql → 0002_souls.sql`.

## CSS Custom Property Theme System
For multi-theme React apps, avoid per-component CSS overrides. Use this pattern:

1. **Root theme variables** live in `themes/<name>.css` under a `.theme-<name>` class selector
2. **App.css** references variables exclusively (`var(--accent-primary)`, `var(--bg-surface)`, etc.)
3. **Backward-compat aliases** in each theme file for old variable names:
   ```css
   --accent-purple: var(--accent-primary);
   --accent-magenta: var(--accent-secondary);
   --glow-purple: var(--glow-primary);
   --glow-magenta: var(--glow-secondary);
   ```
4. **ThemeContext** manages the active theme, persists to localStorage, applies `.theme-<id>` to `<html>`
5. **ThemePicker** component renders the dropdown — position it in the sidebar or settings panel

### Theme file anatomy (7 CSS custom property groups):
- `--bg-*` (primary, secondary, tertiary, hover, surface, raised, overlay)
- `--text-*` (primary, secondary, muted, inverse)
- `--accent-*` (primary, secondary, tertiary, cyan, blue, pink, red, orange, green)
- Semantic (`--success`, `--warning`, `--error`, `--info`)
- `--border-*` (color, glow, light)
- `--glow-*` (primary, secondary, cyan, yellow, green)
- `--gradient-*` (primary, text, sidebar, header, input)
- CRT/Atmosphere (`--crt-opacity`, `--grid-opacity-1`, `--grid-opacity-2`)
- Typography (`--font-body`, `--font-display`, `--font-mono`)
- Layout (`--radius-*`, `--shadow-*`, `--transition-*`)
- `--theme-name`, `--theme-icon` (for the picker UI)

## Server Startup Verification

When verifying a Node.js/tsx server starts, **do not** use `tsx watch` (the `--watch` variant) in background mode — it buffers ALL stdout when backgrounded, making it appear silent even when the server is running fine.

**Reliable pattern** — foreground with `pty=true` and a short timeout:

```bash
# Run the server in foreground with pty so stdout flushes immediately
cd src/backend && timeout 10 npx tsx src/index.ts 2>&1; echo "EXIT_CODE=$?"
```

This flushes every `console.log` immediately. If it exits with code 124 (timeout), the server started and ran successfully until the timeout killed it. If it exits with any other code, something failed — the error output will be visible.

**Background-with-health-check pattern** — if you need the server to keep running:

```bash
# Start in background
cd src/backend && npx tsx src/index.ts 2>&1 &
sleep 3
# Verify health endpoint
curl -s http://localhost:3001/api/health | python3 -m json.tool
```

But there's a catch: background output may flush in bursts. If you get zero output for 5+ seconds, kill it and use the foreground `timeout + pty` approach to see what's happening.

**PITFALL: `npx tsx watch src/index.ts` in background** — The `--watch` variant is designed for interactive development and aggressively buffers in background mode. Never use `tsx watch` for startup verification. Use plain `tsx src/index.ts` instead.

**PITFALL: First-start check order** — When resuming work on a project:
1. Check if PostgreSQL is running (`pg_isready`, `systemctl is-active postgresql`)
2. Check if the server is already running (`curl localhost:PORT/api/health`)
3. Check recent commits (`git log --oneline -10`)
4. Run the foreground timeout check before backgrounding the server
5. If health endpoint returns JSON with `success: true`, the stack is live

## Backend Service Pattern (Drizzle)
```typescript
export class SomeService {
  async create(data: CreateData): Promise<Entity> {
    const id = uuidv4();
    const [entity] = await db.insert(table).values({ id, ...data }).returning();
    return entity;
  }

  async list(filter?: { ... }): Promise<Entity[]> {
    const conditions: SQL[] = [];
    if (filter?.status) conditions.push(eq(table.status, filter.status));
    const query = db.select().from(table);
    if (conditions.length > 0) query.where(and(...conditions));
    return query.orderBy(desc(table.createdAt));
  }

  async update(id: string, data: Partial<UpdateData>): Promise<Entity | null> {
    const [entity] = await db.update(table).set({ ...data, updatedAt: new Date() })
      .where(eq(table.id, id)).returning();
    return entity || null;
  }
}
```

## File Write Corruption Prevention

The `execute_code` tool's `write_file()` can corrupt files when the content has already been read with `read_file`'s line-number prefix format. **SIGNAL: if a file suddenly has hundreds of TypeScript errors like `Expression expected [1109]` on every line, it's been corrupted.**

**Detection:** read the first 5 lines of the file. If you see `1|1|import...` (duplicate line number prefix), the content has the read_file display format baked in.

**Fix:** Use a `delegate_task` subagent with goal "Fix the line-number corruption in <filepath>". The subagent reads the file, strips `\s+\d+|` prefix from every line, and writes clean:

```python
# Inside execute_code — DO NOT USE write_file from here
# The read_file in execute_code returns content WITH line numbers
# Use the direct write_file tool instead
```

**Prevention:** Never pipe content from `read_file()` in execute_code through `write_file()`. The execute_code environment's `read_file` returns content with embedded line-number prefixes. Always use the top-level `write_file` tool (not inside execute_code) when the source is another file read. If you must extract data from execute_code, use `print()` statements and capture stdout.

**Workaround:** For simple find-and-replace operations inside a file, use `patch()` tool instead — it's immune to this issue because it reads the file fresh for each match.

### Key Patterns

**Safe curl wrapper** — handles auth headers, content-type, and error reporting uniformly:
```bash
janus_curl() {
  local method="$1"; shift; local path="$1"; shift; local data="${1:-}"
  local args=(-sS -X "$method")
  args+=("${API_BASE}${path}")
  [ -n "$JANUS_API_KEY" ] && args+=(-H "Authorization: Bearer ${JANUS_API_KEY}")
  args+=(-H "Content-Type: application/json")
  [ -n "$data" ] && args+=(-d "$data")
  curl "${args[@]}" 2>/dev/null || error "HTTP request failed: ${path}"
}
```

**jq-free JSON parsing** — avoid forcing users to install jq:
```bash
json_val() {
  local key="$1"
  if command -v jq &>/dev/null; then
    echo "$json" | jq -r "$key" 2>/dev/null || echo "null"
  else
    echo "$json" | grep -o "\"${key}\"[[:space:]]*:[[:space:]]*\"[^\"]*\"" | \
      sed "s/.*\"${key}\"[[:space:]]*:[[:space:]]*\"//;s/\"//" 2>/dev/null || echo "null"
  fi
}
```

**Auto-registration** — on first use, register with the server, cache the key:
```bash
auto_register() {
  local cache_file="${CACHE_DIR}/registration.json"
  [ -n "$JANUS_API_KEY" ] && return 0
  [ -z "$JANUS_HARNESS_TYPE" ] && return 0
  if [ -f "$cache_file" ]; then
    local cached_key="$(cat "$cache_file" | json_val '.api_key')"
    [ -n "$cached_key" ] && { export JANUS_API_KEY="$cached_key"; return 0; }
  fi
  # Register, extract API key, cache it
}
```

**Environment-driven config** — every behavior comes from env vars with defaults:
```bash
JANUS_HOST="${JANUS_HOST:-http://localhost:3001}"
JANUS_API_KEY="${JANUS_API_KEY:-}"
JANUS_HARNESS_TYPE="${JANUS_HARNESS_TYPE:-}"
JANUS_DEBUG="${JANUS_DEBUG:-}"
```

**PITFALL: jq over grep/sed** — Always prefer `command -v jq &>/dev/null` + fallback. jq is common on dev machines but absent on minimal containers or headless servers. The grep/sed fallback handles simple key extraction but fails on nested objects, arrays, or escaped quotes. For complex JSON, return raw text and let the next processing step handle it.

**PITFALL: CLI binary naming** — The user prefers the bare project name (e.g. `janus`) over `project-cli` (e.g. `janus-cli`). Symlink the primary entry point as `/usr/local/bin/<projectname>`. If a legacy bash script exists under a `-cli` name, symlink both. The user corrected `janus-cli/` → `janus` explicitly. Do not use `-cli` as a default suffix when naming new CLI tools for this user.

## Harness Auto-Registration Endpoint Pattern

For platforms where AI harnesses need to self-onboard dynamically (no prior API key required):

### Endpoint: `POST /api/harnesses/register`

Creates a user account + API key + agent soul + capability registration in one atomic call.

**Request body:**
```json
{
  "name": "synthclaw",
  "type": "hermes-agent",
  "model": "deepseek-v4-flash",
  "strengths": ["orchestration", "multi_agent"],
  "personality": "Orchestrator...",
  "backstory": "Born from the VHS static...",
  "auto_create_soul": true
}
```

**Response:**
```json
{
  "success": true,
  "data": {
    "apiKey": "janus_xxx...",
    "agentId": "uuid",
    "soulId": "uuid",
    "name": "synthclaw",
    "type": "hermes-agent"
  }
}
```

### Per-Harness Metadata Pattern

Use lookup tables keyed by harness type for default personalities, backstories, archetypes, and strengths:

```typescript
const archetypeMap: Record<string, string> = {
  'hermes-agent': 'commander',
  'claude-code': 'sage',
  'codex-cli': 'creator',
  'gemini-cli': 'explorer',
};
```

Each harness gets a tailored `personality` (role description), `backstory` (narrative origin), and `strengths` (capability tags). These feed directly into the Agent Soul system — the soul's `personality`, `backstory`, `expertiseTags`, and `archetype` fields.

### Implementation Flow

1. Generate agent UUID
2. Insert user row (type: 'ai') into users table
3. Generate API key via `crypto.createHash('sha256').update(rawKey).digest('hex')`
4. Insert api_key row with SHA-256 hash, prefix, permissions, expiry
5. Create agent soul via soulService.createSoul() with per-harness metadata
6. Activate soul immediately (status: 'active')
7. Register capability via capabilityRegistry
8. Return raw API key (shown once — not stored in DB)

**PITFALL: `import('crypto')` in TypeScript** — Node.js crypto is native but TypeScript may not have `@types/node` loaded in the route file's scope. Use dynamic `await import('crypto')` at the call site instead of a static `import * as crypto from 'crypto'` at the top of the file. Works in both ESM and CJS modes.

**PITFALL: Drizzle `db.insert()` with `.returning()`** — Works for PostgreSQL (Drizzle v0.39+). If TypeScript complains about missing properties on the store, import `db` from `../db/index.js` and the schema objects directly rather than going through `store.db` / `store.schema`:

```typescript
import { db } from '../db/index.js';
import { users } from '../db/schema.js';
import { apiKeys } from '../db/schema.auth.js';
// NOT: store.db.insert(store.schema.users) ← store may not expose db/schema
```

## Python SDK Harness Adapter Architecture

For projects that need a multi-harness SDK with auto-detection and a factory pattern:

### Base Class Pattern

```python
class BaseHarnessAdapter(ABC):
    @property
    @abstractmethod
    def harness_type(self) -> HarnessType: ...
    @property
    @abstractmethod
    def capabilities(self) -> HarnessCapabilities: ...

    async def connect(self) -> None:
        await self.connect_to_janus()
        print(f"🔧 Connected as {self.agent_name}")

    async def connect_to_janus(self) -> None:
        config = ConnectionConfig(base_url=self.janus_url, api_key=self.api_key)
        self._janus_client = JanusClient(config)
        await self._janus_client.connect()
```

### Factory Pattern with Dynamic Registration

```python
class HarnessAdapterFactory:
    _adapters = {
        HarnessType.OPENCLAW: OpenClawAdapter,
        HarnessType.CLAUDE_CODE: ClaudeCodeAdapter,
        # ... 13+ adapters
    }

    @classmethod
    def create_adapter(cls, harness_type, **kwargs):
        adapter_class = cls._adapters.get(harness_type)
        if not adapter_class:
            raise ValueError(f"Unknown harness type: {harness_type}")
        return adapter_class(**kwargs)

    @classmethod
    def register_adapter(cls, harness_type, adapter_class):
        cls._adapters[harness_type] = adapter_class

    @classmethod
    def detect_harness_from_env(cls) -> Optional[HarnessType]:
        import os
        if os.getenv("HERMES_AGENT_MODE"): return HarnessType.HERMES_AGENT
        if os.getenv("GEMINI_API_KEY") or os.getenv("GEMINI_CLI_ACTIVE"): return HarnessType.GEMINI_CLI
        if os.getenv("CODEX_CLI_ACTIVE"): return HarnessType.CODEX_CLI
        if os.getenv("CLAW_CODE_WORKSPACE"): return HarnessType.CLAW_CODE
        # ... per-harness env var checks
```

### Adapter Example
Each adapter implements ~8 methods. The pattern is consistent — only the `print()` prefix icon changes:

```python
class HermesAgentAdapter(BaseHarnessAdapter):
    @property
    def harness_type(self) -> HarnessType:
        return HarnessType.HERMES_AGENT

    @property
    def capabilities(self) -> HarnessCapabilities:
        return HarnessCapabilities(supports_subagents=True, supports_tools=True)

    async def connect(self) -> None:
        await self.connect_to_janus()
        print(f"🔱 Hermes Agent connected to Janus as {self.agent_name}")

    async def get_context(self) -> HarnessContext:
        import os
        return HarnessContext(harness_type=self.harness_type, workspace_path=os.getcwd())
```

**PITFALL: Shared print() in both connect() and send_to_user()** — The base class `connect()` prints a connection message. Each adapter's own `connect()` calls `await self.connect_to_janus()` (which doesn't print) then prints its own message. If you accidentally call `super().connect()` instead of `connect_to_janus()`, you get double-prints. Override `connect()` to call `connect_to_janus()` + your own print, not `super().connect()`.

## Vite Proxy Configuration

For local development, avoid hardcoded backend URLs in frontend code. Use Vite's dev server proxy:

```typescript
// vite.config.ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      '/api': { target: 'http://localhost:3001', changeOrigin: true },
      '/socket.io': { target: 'http://localhost:3001', ws: true, changeOrigin: true },
    },
  },
})
```

**Client changes:**
- `API_BASE` in `api/client.ts`: `'http://localhost:3001/api'` → `'/api'`
- Socket.IO in `hooks/useSocket.ts`: `io('http://localhost:3001')` → `io()` (empty string = current origin)
- All fetch calls use relative paths through the proxy

**Benefits:** No CORS in dev, single origin in production, easy to swap backends by changing proxy target.

## React Frontend Polish Patterns

### 1. Zero-Dependency Markdown Renderer

Avoid pulling in `react-markdown` + plugins (~50KB gzip) when basic rendering is enough. Build a lightweight one:

See `references/react-markdown-renderer.md` for the full implementation — component, block renderer, inline renderer, and CSS.

**Two-phase render**: block-level (code blocks, paragraphs, HRs) → inline (code, bold, italic, links, images, strikethrough). No deps beyond React.

**Block-level** — match ` ```lang\n content ``` ` first, then process line-by-line. Empty lines → `<br>`, `---` → `<hr>`, text → `<p>{inline}</p>`.

**Inline** — character-by-character regex precedence: `` `code` `` → `![alt](url)` → `[text](url)` → `***b+i***` → `**bold**` → `*italic*` → `__bold__` → `_italic_` → `~~strike~~` → plain char.

**PITFALL:** Check bold+italic (`***text***`) BEFORE bold (`**text**`) — if you check bold first, `***text***` matches as `**text**` with trailing `*`.

### 2. Streaming Message Indicators

For AI streaming via Socket.IO:

- Messages with `authorId === 'streaming'` and empty content are in-flight. Disable input while streaming.
- **Blinking cursor** (`▊` with `animation: cursorBlink 0.8s step-end infinite`) in the empty message body.
- **Dot bar** — three animated dots (`animation: dotPulse 1.4s`) with "AI is generating..." between messages and input.
- **Dimmed** — `opacity: 0.7` on `.message.streaming`.

### 3. Collapsible Responsive Sidebar

React state: `const [collapsed, setCollapsed] = useState(false)`.

- Hamburger toggle (`max-width: 768px`), sidebar slides with `transform: translateX(-100%)`.
- Overlay backdrop (`z: 90`), sidebar (`z: 100`), toggle (`z: 110`).
- Auto-collapse after navigation on mobile: `if (window.innerWidth < 768) setCollapsed(true)`.

### 4. Auto-Resizing Textarea

```tsx
const textareaRef = useRef<HTMLTextAreaElement>(null);
useEffect(() => {
  const ta = textareaRef.current;
  if (ta) { ta.style.height = 'auto'; ta.style.height = Math.min(ta.scrollHeight, 120) + 'px'; }
}, [inputValue]);
```

### 5. Better Message Timestamps

Show time-only for today, add date for older: `d.toDateString() === now.toDateString()` → time-only, else `MMM dd HH:mm`.
